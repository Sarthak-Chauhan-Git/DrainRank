# DrainRank Supabase Setup

## Existing Supabase project

The project is shared by the citizen app, web dashboard, and field app. The
existing schema and access model are retained:

- `profiles`: Auth-linked users with `citizen`, `crew`, and `admin` roles;
- `citizen_reports`: existing report table, using `reporter_id` and
  `image_sha256_hash`;
- `dashboard_state`: existing JSON state table with `id`, `payload`,
  `updated_at`, and `updated_by`;
- `credit_awards` and `leave_requests`: existing tables that store app-specific
  details in `payload`;
- `staff_accounts`: existing table; its unlinked row is retained.

The signup trigger creates a citizen profile. The project administrator was
created in Supabase Auth and promoted to `profiles.role = 'admin'`. Email
authentication is enabled and email confirmation is required.

Two private Storage buckets have been created and configured with a 10 MB
limit and image MIME types:

- `citizen-photos`: owner-folder upload/delete and citizen/staff read policies
  have been created;
- `work-photos`: the migration adds assigned-crew upload, authorized read, and
  own-photo delete policies.

Do not run the original, incompatible migrations from prior drafts. The
checked-in migrations were rewritten to reuse the discovered schema:

1. `backend/supabase/migrations/202610210001_shared_app_backend.sql`
2. `backend/supabase/migrations/202610220001_web_dashboard_state.sql`

Both migrations have now run successfully in Supabase SQL Editor. The
`create-crew-account` Edge Function has also been deployed to the linked
project.

## What the migrations add

The shared-app migration:

- adds `image_path` to `citizen_reports` only if missing;
- creates `field_tasks` and `field_work_updates`, with RLS based on the
  existing `profiles` roles and `is_admin()` / `current_profile_role()` helper
  functions;
- adds protected RPCs for dashboard task synchronization, field work
  submission, credit grants, and overdue deductions;
- writes awards to the existing `credit_awards` table and adds own-row/admin
  read policies for credits and leave requests without replacing other
  existing policies;
- leaves the existing `leave_requests`, `profiles`, `citizen_reports`,
  `dashboard_state`, and `staff_accounts` policies intact; and
- adds RLS policies for the private `work-photos` bucket.

The dashboard migration adds optimistic-concurrency save and report-status RPCs
using the existing `dashboard_state` table and admin helper. It does not create
`dashboard_admins` or `web_dashboard_state`.

## Deployment status and checks

1. In the Supabase Dashboard, make sure the project is backed up or export a
   backup first.
2. Open and review the two migration files above. Confirm the `is_admin()` and
   `current_profile_role()` helpers still match the definitions already
   inspected.
3. Applied successfully: both complete migrations, in timestamp order.
4. Applied successfully: Edge Function deployment:

   ```powershell
   Set-Location backend
   npx supabase functions deploy create-crew-account --project-ref YOUR_PROJECT_REF
   ```

   The function uses Supabase's server-managed service key. Never place a
   service-role key in app code, client environment files, or chat.

5. Still required: verify the new tables/RLS and run the app smoke tests below.
   Keep both photo buckets private.

## App-specific setup and smoke tests

Use the same Supabase project URL and publishable key in all three apps.

### Citizen app

- Email provider enabled; new sign-ups allowed; email confirmation enabled.
- Signup trigger creates `profiles.role = 'citizen'`.
- `citizen_reports` insert/read policies and the private `citizen-photos`
  policies are already configured.
- Test: sign up, confirm email, sign in, submit a report, then verify the owner
  can see the report and a signed photo URL.

### Web dashboard

- Sign in with the administrator whose active profile has role `admin`.
- Dashboard code uses existing `profiles`, `dashboard_state`, and
  `citizen_reports`, plus the new `field_tasks` table.
- Dashboard evidence uploads remain on the existing Cloudinary configuration;
  citizen and field photos use Supabase Storage.
- Test: load/save dashboard state, view a citizen report, update its status,
  and assign a work order to a worker whose ID exactly matches a crew
  Municipal ID.

### Field app

- Admin provisions crew accounts through `create-crew-account`; the function
  creates an Auth user and updates the trigger-created profile to role `crew`.
- Crew login is Municipal ID/password; the internal Auth email is generated by
  the app and function.
- Test assigned task visibility, evidence photo upload/submission, leave
  request insertion, credit approval, and rejection for blocked/unassigned
  accounts.
